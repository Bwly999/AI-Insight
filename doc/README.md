# AI Insight · 文档导航

> **The Insight Review** — 内网私有化部署的 AI 洞察周刊平台
> 双模式：①订阅推送（系统周期跑）②主动洞察（Pi Agent 自主采集分析）

## 两层职责

| 层 | 目录 | 写给谁 | 内容形态 | 改动频率 |
|---|---|---|---|---|
| **概念层** | `design-doc/` | 人（架构师 / 评审 / 运营） | 为什么这么设计、决策依据、概念图 | 低（决策定型后少改） |
| **执行层** | `dev-spec/` | 施工 Agent（也给人 review） | 做什么、接口签名、文件路径、验收点 | 高（随实现迭代） |

**规则**：dev-spec 不重复 design-doc 的概念推理，只链接引用；design-doc 不写实现细节，只写决策与依据。两层冲突时，**design-doc 为准**（执行层若发现设计问题，应回到 design-doc 改决策，再同步 dev-spec）。

## 「我是谁 · 我要做什么」决策表

| 场景 | 先看 | 再看 |
|---|---|---|
| **第一次了解项目** | `design-doc/00-决策摘要` | `design-doc/01-项目概述` → `02-系统架构` → `16-双模式架构` |
| **评审架构合理性** | `design-doc/02` + `05-SPI` + `06-数据模型` | `design-doc/16`（双模式） |
| **开始写某 Phase 代码** | `dev-spec/README`（任务卡格式） | `dev-spec/0X-{Phase}.md` + 引用的附录 A/B/C |
| **查某个表/接口长什么样** | `dev-spec/A-数据契约` | `dev-spec/B-API清单` |
| **确认某功能是否验收通过** | `dev-spec/C-验收矩阵` | 对应 `dev-spec/0X` 的任务卡「验收点」段 |
| **某留白项的默认值/谁定** | `dev-spec/D-留白决策记录` | `design-doc/14-留白与后续确认` |
| **接内网扩展点（采集器/通道/LLM）** | `design-doc/05-SPI` + `11-内网扩展点` | `dev-spec/A` 的 SPI 接口签名 |
| **前端做页面** | `design-doc/15-UIUX` + `08-前端架构` | `dev-spec/03` 用户端任务卡 |
| **部署/运维** | `design-doc/09-基础设施与部署` | `dev-spec/05-加固` |

## 阅读约定

- **`★` 标记**：核心文档（决策源头），改动需评审。
- **「留白」**：待使用方在内网填的项，见 `dev-spec/D`。
- **「依据」引用**：dev-spec 文档顶部的 `> 依据：design-doc/XX.md §Y` 表示该规格的概念出处。
- **任务卡编号**：`任务 X.Y` 中 X = Phase 数字，Y = 卡序号，可在 `C-验收矩阵` 反查。
- **代码块**：dev-spec 的 TS 代码块是**接口签名 / 数据结构**（非完整实现），完整实现由施工 Agent 完成。
- **文件路径**：dev-spec 中所有路径相对项目根（如 `apps/server/src/...`）。

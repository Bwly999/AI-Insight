## 2.2 组件职责

| 组件 | 职责 |
|---|---|
| **用户端 SPA** | 读本期/往期报告、订阅设置、反馈/收藏 |
| **管理端 SPA** | 数据源、领域、调度目标、cron、代理、报告查看/重推、用户/角色、通道管理 |
| **外部登录服务** | 使用方提供，签发含 `id`/`name` 的 JWT |
| **Fastify 后端** | 认证守卫、REST API、SPI 注册、cron 调度、BullMQ worker |
| **MySQL + Drizzle** | 全部业务数据持久化 |
| **Redis + BullMQ** | 采集/处理/报告/推送任务队列 |
| **内网 LLM 服务** | OpenAI 兼容地址，Vercel AI SDK 调用，仅 chat |
| **HTTP 代理** | 管理端配置，应用内自定义客户端，用于 RSS/搜索出网 |
| **采集器 SPI** | RSS / SearchApi / SearchCrawl / Playwright(预留) |
| **推送通道 SPI** | ConsoleNotifier(默认) + 内网实现 |

## 2.3 数据流（端到端）

```
① 采集 (全局 cron, 如每 30min)
   scheduler → 遍历 enabled Sources → 每源一个 BullMQ job
   collection.worker → ICollector.fetch → 算 fingerprint → 去重 → 落 RawItem → 写 CollectLog
   (出网经 http-client 插件走管理端配置代理)

② AI 处理 (全局处理一次, 独立 cron 或攒批触发)   ← LLM 唯一重阶段, 与用户数无关
   processing.worker 五阶段:
     a) 清洗去重: 指纹 + LLM 语义判重
     b) 分类打标: generateObject → categoryCode + tags
     c) 摘要:     generateText → 中文 summary
     d) 热度:     generateObject → heat(0-100) + critical
     e) 综合:     generateText → 领域点评 / 趋势总结 / 编辑荐语 (深度报告)
   → 落 Article 池 (全局共享)

③ 报告生成 + 推送 (按 ReportSchedule 的 cron 触发)
   report.worker → 对该 schedule 下每个 active Subscription:
     按 categoryCodes ∪ keywords 命中, 从 Article 池裁剪
     选该用户头条 + 组装 bodyJson (含个性化点评)
     → 落 Report(READY) → delivery.worker
     → 按 Subscription.channels → INotificationChannel.send
     → ConsoleNotifier 打印 / 内网通道推送 → 写 NotificationLog
```

## 2.4 关键架构特性

### 成本与用户数解耦
- 阶段 ② 是唯一调用 LLM 的重阶段，全局只跑一次。
- 阶段 ③ 报告生成仅做裁剪 + 组装，不调 LLM。
- 因此 LLM 调用成本与用户数无关，仅随「处理批次的 Article 数」增长。

### 三处零改核心代码扩展
- **采集器**：实现 `ICollector` + `fastify.registerCollector(type, impl)`。
- **推送通道**：实现 `INotificationChannel` + `fastify.registerNotifier(channel, impl)`。
- **LLM**：改 `llm.ts` 插件的 `baseURL` 指向不同内网模型服务。

### 内网边界清晰
- 出网仅限 RSS/搜索，经管理端配置的自定义代理。
- LLM、数据库、Redis、推送通道全部在内网。
- 登录由外部服务签发 token，后端只验不签。

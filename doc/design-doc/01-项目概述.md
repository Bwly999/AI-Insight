# 01 · 项目概述

## 1.1 产品定位

一个部署在企业内网（<50 人单团队）的 AI 洞察平台。它从 RSS、搜索引擎等数据源**定时采集**领域资讯，经内网大模型 **AI 处理**（去重、分类、摘要、热度评估、趋势点评），整理为**深度中文报告**，按用户订阅偏好**个性化裁剪**后**推送**给用户。

系统分为两套前端：
- **用户端**：读报告、订阅、反馈
- **管理端**：配数据源、调度、查看运行

## 1.2 典型使用场景

1. 管理员在管理端配置若干 RSS 源 + 搜索引擎 API + 一个 HTTP 代理（出网用）。
2. 平台按全局 cron 定时采集，原始内容入库去重。
3. 平台按全局处理 cron 用内网 LLM 统一处理：分类、中文摘要、热度、趋势点评，产出共享 Article 池。
4. 管理员定义报告调度目标（如「每日早报」cron=`0 6 * * *`、「每周周报」cron=`0 8 * * 1`）。
5. 用户在用户端订阅：勾选领域 + 填关键词 + 挂载到某个调度目标 + 选推送通道。
6. 调度目标 cron 触发 → 为该目标下每个用户裁剪组装 Report（实体化存档）→ 按用户通道偏好推送。
7. 用户打开用户端看到本期报告，可往期浏览、反馈、收藏。

## 1.3 设计原则

1. **双系统分离**：用户端与管理端独立 SPA，共享一套后端 API 与数据库。
2. **三处可插拔（SPI）**：采集器（`ICollector`）、推送通道（`INotificationChannel`）、LLM 均定义统一契约，复杂/内网实现可零改核心代码接入。
3. **成本与用户数解耦**：AI 全局处理一次产出共享 Article 池；推送时仅做裁剪组装，不再调用 LLM。
4. **内网优先**：纯私有化部署；LLM 走内网模型服务；仅搜索/RSS 出网，且经管理端配置的自定义代理。

## 1.4 关键决策清单

详见 [00-决策摘要](./00-决策摘要.md)。摘要：

| 维度 | 决策 |
|---|---|
| 部署 | 纯内网私有化；LLM 用内网模型服务；仅搜索/RSS 出网 |
| 规模 | <50 人，单团队，无多租户 |
| 认证 | 外部登录 + Bearer token + jose 解 JWT + 后端查库定角色 |
| LLM | Vercel AI SDK，仅 chat，无 embedding |
| 采集 | 统一 `ICollector`：RSS + 搜索分型 + Playwright 预留 |
| 报告调度 | 按 ReportSchedule 配置 cron；采集/处理仍全局统一 |
| 质量控制 | AI 全自动打分直推，审稿不阻塞 |
| 订阅 | 领域 + 关键词 |
| 报告形态 | 统一中文，深度报告 |
| 推送 | 统一 Payload + ConsoleNotifier 默认实现 |
| 前端 | 纯 SPA + Nginx + Tailwind |
| 后端 | Fastify + TypeScript |
| 数据库 | MySQL + Drizzle ORM |

## 1.5 名词表

| 术语 | 含义 |
|---|---|
| RawItem | 采集到的原始条目（未处理） |
| Article | AI 处理后的结构化条目（全局共享池） |
| Report | 为某用户某期组装的报告实体（可存档） |
| Source | 数据源（采集层概念，用户不直接订阅） |
| Category | 领域（管理端定义，如 AI/BIO/QUANT） |
| Subscription | 用户订阅（领域 + 关键词 + 挂载的 schedule + 通道） |
| ReportSchedule | 报告调度目标（管理端定义，各自 cron） |
| Collector | 采集器（`ICollector` 实现） |
| Channel | 推送通道（`INotificationChannel` 实现） |

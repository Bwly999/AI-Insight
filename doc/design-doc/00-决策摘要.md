# 00 · 决策摘要

本平台经逐项盘问（grill）确认的关键技术决策速查表。所有后续文档以此为准。

## 核心决策清单

| 维度 | 决策 |
|---|---|
| **部署环境** | 纯内网私有化部署；LLM 用**内网模型服务**；仅搜索/RSS 出网 |
| **用户规模** | <50 人，单团队，**无多租户** |
| **认证** | 外部登录服务取 token → `Authorization: Bearer <token>` 请求头 → 后端 `jose` 解 JWT 取 `id`/`name` → **后端查库定 USER/ADMIN 角色**；**后端不实现登录接口**（秘钥与解包留白由使用方填） |
| **LLM** | **Vercel AI SDK**（不手写 provider），**仅 chat、无 embedding** |
| **采集** | **统一 `ICollector`** 接口；内置 RSS + 通用搜索（内部分型 `SEARCH_API`/`SEARCH_CRAWL`）+ **Playwright 能力预留**（深度后补） |
| **AI 处理** | **全局 AI 处理一次** → 产出共享 Article 池（成本与用户数解耦） |
| **报告调度** | **按「订阅目标（ReportSchedule）」配置 cron** —— 管理端定义若干调度目标（如日报/周报），用户订阅挂载到目标；目标 cron 触发时为其下所有用户裁剪组装 Report 并推送 |
| **质量控制** | **AI 全自动打分直推**，审稿不阻塞（管理端「事后纠错」为可选辅助） |
| **订阅维度** | **领域 + 关键词**；领域由管理端统一定义 |
| **报告形态** | **统一中文**；**深度报告**（单条摘要 + 领域点评 + 趋势总结 + 编辑荐语） |
| **数据源运营** | 数据源是**采集层概念**（用户不直接订阅源）；**采集 = 全局统一 cron** |
| **存档** | **只按期浏览往期报告**，不做全文检索 |
| **推送 SPI** | **统一 Payload**；内置 `ConsoleNotifier`（本地打印）默认实现；邮件/企微/飞书等**内网按接口实现** |
| **管理端推送** | **看日志 + 手动重推** |
| **用户端范围** | **报告 + 订阅设置 + 反馈/收藏** |
| **前端** | **纯 SPA + Nginx + Tailwind**（保留原型编辑风设计系统） |
| **后端框架** | **Fastify + TypeScript**（插件 + decorate 模式，无重 DI 容器） |
| **数据库** | **MySQL + Drizzle ORM**（mysql-core） |
| **Phase 0** | 架构骨架：Monorepo + Fastify + Vue3 + MySQL + Drizzle |

## 决策依据要点

### 为什么内网 LLM + 仅 chat
- 内网部署无法访问公网商用 LLM API，模型服务由内网提供。
- 仅 chat（无 embedding）简化技术栈：去重走「指纹 + LLM 语义判重」，**无需 pgvector / 向量库**。

### 为什么成本与用户数解耦
- AI 处理只全局跑一次产出共享 Article 池。
- 报告生成（裁剪+组装）几乎不调 LLM，因此 LLM 成本与用户数无关。

### 为什么用 Fastify 而非 NestJS
- 轻量、高性能，插件 + decorate 模式天然适配「可插拔 SPI」。
- 无重 DI 容器，扩展点注册更直观。

### 为什么报告 cron 按订阅目标配置
- 不同报告（日报/周报）需独立 cron。
- 用户订阅时挂载到某个调度目标，目标 cron 触发时批量处理该目标下所有用户。
- 采集/处理 cron 仍为全局统一。

### 为什么推送只定义接口 + ConsoleNotifier
- 使用方明确诉求：「复杂推送渠道需要在内网自行实现」。
- 平台提供统一 `INotificationChannel` 接口 + ConsoleNotifier 打印默认实现，内网按接口注册 Email/企微/飞书等，**核心代码零改动**。

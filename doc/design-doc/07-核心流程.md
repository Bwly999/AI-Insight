# 07 · 核心流程

## 7.1 认证链路

```
[外部登录服务 使用方提供] --登录--> 返回 token (JWT, 内含 id+name)
[前端] 路由加载时存 token → axios 请求拦截器注入 Header: Authorization: Bearer <token>
[Fastify] auth 插件 preHandler:
    1. 从 header 提取 token
    2. jose 解包 → { id, name }           ← 秘钥配置 + 解包逻辑「留白」由使用方填
    3. SELECT role FROM users WHERE externalId = id   ← 后端查库定角色
       (首次见到 externalId 时按策略自动建 USER 记录, 见 14-留白)
    4. request.user = { id, name, role }
[守卫] admin 路由检查 request.user.role === 'ADMIN', 否则 403
```

### 留白点（使用方实现）
- JWT 秘钥来源（环境变量 / 配置中心）。
- jose 解包的 claims 解析逻辑。
- `externalId` 与本地 `users` 表的映射策略（建议：首次见到自动建 USER 记录）。

### 平台不实现
- 登录 / 注册 / 登出接口。
- 密码存储。

### 前端 axios 拦截器
```ts
axios.interceptors.request.use(cfg => {
  const token = getTokenFromLoginService(); // 调用使用方登录接口取得 token
  if (token) cfg.headers.Authorization = `Bearer ${token}`;
  return cfg;
});
axios.interceptors.response.use(
  r => r,
  err => {
    if (err.response?.status === 401) redirectToLogin(); // token 失效
    return Promise.reject(err);
  }
);
```

## 7.2 报告调度模型

三类 cron，职责分离：

| cron | 粒度 | 说明 |
|---|---|---|
| **采集 cron** | 全局统一 | 如 `*/30 * * * *`，遍历所有 enabled sources，每源入 collection-queue |
| **处理 cron** | 全局统一 | 如 `0 * * * *`，触发一次全局 AI 处理，产出共享 Article 池 |
| **报告 cron** | **按 ReportSchedule** | 每个 schedule 独立 cron，如日报 `0 6 * * *`、周报 `0 8 * * 1` |

### 报告 cron 触发逻辑
```
某 ReportSchedule 的 cron 到点 →
  report.worker:
    查该 schedule 下所有 active subscription
    对每个 subscription:
      按 categoryCodes ∪ keywords 命中 Article 池（取 periodHours 时间窗内）
      选该用户头条（命中中 heat 最高且 critical 优先）
      组装 bodyJson（条目 + 个性化点评片段）
      落 Report(READY)
      入 delivery-queue
```

### 成本关键
- 处理 cron 全局只跑一次 LLM（阶段 ②）。
- 报告 cron 仅做裁剪 + 组装，**不调 LLM**。
- 因此 LLM 成本与用户数无关。

## 7.3 AI 处理五阶段（仅 chat，Vercel AI SDK）

processing.worker 对一批 raw_items 执行五阶段，每阶段独立可重试：

| 阶段 | SDK 调用 | 产出 |
|---|---|---|
| **a 清洗去重** | `generateText` | 判定相似条目，标记丢弃 |
| **b 分类打标** | `generateObject` + zod | `categoryCode + tags` |
| **c 摘要** | `generateText` | 中文 `summary`（外文源翻译概括为中文） |
| **d 热度** | `generateObject` + zod | `heat(0-100) + critical` |
| **e 综合** | `generateText` | 领域点评 / 趋势总结 / 编辑荐语（深度报告） |

### 结构化产出示例（阶段 b）
```ts
const { object } = await generateObject({
  model: fastify.llm.chat,
  schema: z.object({
    categoryCode: z.enum(['ai','bio','quant','climate','soc']),
    tags: z.array(z.string()).max(5),
  }),
  prompt: `对以下内容分类并打标（输出中文标签）：\n${rawText}`,
});
```

### 中文输出约束
所有 `generateText` / `generateObject` 的 prompt 显式要求中文输出；外文源由 LLM 翻译概括为中文。

## 7.4 采集流程

```
采集 cron 到点 →
  对每个 enabled source:
    入 collection-queue
collection.worker:
  collector = fastify.collectors.get(source.type)
  items = await collector.fetch(source)          // 经 fastify.http 出网（走代理）
  for item in items:
    fp = hash(normalizeUrl(item.url) + item.title)
    if raw_items.fingerprint 不存在 fp:
      insert raw_item
      itemsNew++
  update collect_logs(SUCCESS, itemsFetched, itemsNew)
失败 → BullMQ 指数退避重试 → 死信队列 → collect_logs(FAILED, error)
```

## 7.5 推送流程

```
Report(READY) 产生 → 入 delivery-queue
delivery.worker:
  for channel in subscription.channels:
    impl = fastify.notifiers.get(channel)       // 默认 ConsoleNotifier
    result = await impl.send(notificationPayload)
    insert notification_logs(channel, status, payload, error)
失败 → 记 FAILED → 管理端可「手动重推」重新入队
```

## 7.6 事后纠错（可选，不阻塞主流程）

管理员在管理端可对已生成的 Article 修改 `summary / heat / critical`，修改持久化但不触发自动重推（需手动重推受影响报告）。此能力为辅助，主流程全自动直推。
